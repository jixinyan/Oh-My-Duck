# Agentic Microduck · 分步执行计划 v0.2

设计依据：[项目设计 v0.1](Agentic%20Microduck%20-%20Project%20Design%20v0.1.md)。本文件把设计拆成可以逐项开发、验收的工作单，不改变已确定的项目范围。文件名保留以维持引用；内容已按用户确认的双训练后端范围更新。当前第 01–02 步进行中，其他步骤按下表推进；设计文档与流程图不计作功能实现。

**执行顺序：先建立完整项目框架与模块契约 → 审读并建立可独立使用的官方 MuJoCo 训练后端 → 完成 Isaac/Newton 后端与 sim2sim → 打通通用工具与 mock/真实 Harness → 加入语音和持久音色 → 加入感知与完整体验 → 发布可复现版本。**

第一个核心成果是：在 Isaac 中训练出行走策略，经官方格式导出和官方回放验证，能够进入真机验证。语音与复杂视觉任务建立在这条运动控制链路之上。

| 15 | 完成目标交互、经验记录与整体演示 | 找球 / 接近 / 停止 / 反馈的可追溯体验 | M3 / M4 |
| 16 | 整理安装、评测与扩展教程 | 他人能独立复现和扩展的开源 v0.1 | M4 |

这是单条主线的建议顺序。第 08 步需要真机：如果设备暂未到位，记录为待验证，可以继续第 09–12 步的仿真和电脑音频工作。没有真机结果时不宣称 sim-to-real 已完成。外部 Harness 尚未就绪时可使用确定性 stub 验证连接，但不能把 stub 演示算作自主 agent 已完成。

## 2. 每一步的工作与通过条件

### 第 00 步：先建立服务完整项目的框架

按用户最新要求，在继续具体功能前建立共享契约、RobotBackend、SkillRunner、ToolCatalog、ActivePerception、PolicyAdapter、HarnessBridge、语音服务协议、EpisodeRecorder、离线 TrainingBackend 与应用装配。核心包不能隐式加载模拟器或模型；依赖从实现层指向契约层。

**通过条件**：入口可发现；模块职责、依赖和后续接入方式有文档；未实现能力明确不可用；边界测试覆盖依赖隔离、请求关联、仿真/现实记录分隔和禁止 Newton 静默降级；原设计、README 总览和进度同步。

**后续顺序**：完成框架后依次填充下述功能。框架通过不等于语音、真实工具闭环或两种训练环境均已验证。

### 第 01 步：读透官方代码，形成工程地图

**目的**：把“项目大致怎么工作”变成“每个关键行为由哪个文件、函数、配置和服务负责”。这是下一次正式开始执行时应做的第一项任务。

工作内容：

- 固定两个官方仓库的提交版本，建立完整文件清单，逐项记录用途和阅读覆盖；资产、生成文件与外部依赖单独标明，不将关键文件抽查称为全库审计。
- 跟踪训练主链：启动入口 → 机器人资产 → actuator → 观测 / 动作 → reward / reset → PPO → checkpoint → exporter。
- 跟踪执行主链：策略加载 → 61 维观测构建 → 14 维动作后处理 → 关节控制；同时核对速度、注视、状态及停止接口。
- 核查相机、ToF、双 IMU、音频采集 / 播放的实际调用路径，列出已存在接口与需要新建的适配。
- 列出 BAM 依赖的底层物理字段、调度频率与状态缓存，形成 Isaac 迁移差异表。
- 确认 Linux 主机的连接方式、GPU / 显存、驱动与存储条件，确认是否有真机及其版本；获取可用的外部 Harness 接口材料。
- 记录代码、资产和模型的许可证及分发条件，保留来源。

**交付物**：上游审读报告、源码定位表、官方策略契约、迁移检查清单、环境与硬件清单。

**通过条件**：能够指向具体实现，解释一次训练样本如何产生，以及一个 ONNX 动作最终如何作用于舵机；剩余不确定项均有明确的核查方法。

**具体例子**：不能只写“动作是 14 维”，还要列出 14 个关节顺序、默认姿态、缩放 / 裁剪方式，以及嘴部为什么单独处理。

### 第 02 步：先让官方项目完整跑起来

**依赖**：第 01 步；可用 Linux + NVIDIA 主机。

工作内容：

- 在独立环境安装固定版本的官方训练项目，保存实际依赖版本和启动配置。
- 用官方已发布且匹配版本的策略运行平地行走回放，记录输入命令、输出、视频与指标。如果没有可用权重，先通过官方训练生成基线，并记录这项额外工作。
- 跑一次短训练，验证环境 reset、奖励、日志、checkpoint 保存和恢复；短训练只证明管线可用。
- 完成一次导出，再用官方 CPU MuJoCo 路径加载和回放。
- 固定前进、转弯、停止等评测序列和初始状态，记录速度跟踪误差、跌倒、脚滑及计算资源。
- 根据测得的基线确定迁移比较的场景、样本和可接受退化范围，写入评测配置。

**交付物**：官方参考环境、可重现命令、基线策略 / 视频 / 指标、导出回放记录。

**通过条件**：重新启动环境后能够重复运行同一条官方链路；评测不依赖手动临时改代码。

**具体例子**：使用同一段“前进 → 左转 → 停止”的命令序列，之后分别交给官方环境和 Isaac 环境。

### 第 03 步：建立最小工程，把机器人放进 Isaac

**依赖**：第 01–02 步。

工作内容：

- 扩展第 01–02 步已建立的代码仓库：公共契约位于 `src/oh_my_duck/core/`，评测位于 `rl/evaluation/`，两个仿真后端位于 `rl/backends/{mujoco,isaac_newton}/`。任务、MDP 与原生 PPO 分别位于 `rl/tasks/`、`rl/mdp/`、`rl/learners/`；其他领域按整体项目 scope 逐步实现。
- 根据官方支持情况选择并固定 Isaac Lab、Newton 与 MuJoCo-Warp 的兼容组合；将选择理由和限制写入版本记录。
- 运行选定后端的最小物理示例，确认 GPU 物理步骤可执行。
- 导入 Microduck 资产，核对几何、关节、质量惯量、碰撞、坐标轴、足部和默认姿态；需要转换时保留可重现的转换过程。
- 创建一个平地场景，支持初始化、状态读取、仿真步进与 reset。

**交付物**：版本锁定文件、资产导入过程、最小平地场景、导入前后参数对照。

**通过条件**：机器人结构和物理参数正确；可以重复 reset 并读取所有需要的关节状态。此时能显示机器人不等于已经完成行走迁移。

### 第 04 步：迁移执行器，先验证物理响应

**依赖**：第 03 步。

工作内容：

- 迁移目标基线所使用的 BAM 电机行为、摩擦、电压相关项和动作延迟。
- 核查 Isaac / Newton solver 中哪些行为由引擎处理、哪些由自定义 actuator 处理，避免重复摩擦或阻尼。
- 比较单关节阶跃响应、静态负载、动作延迟和足部接触。
- 验证多个并行环境的缓存和随机化相互独立，reset 能清空旧状态。
- 按目标基线决定是否需要齿隙变体；不把它默认塞进第一次迁移。

**交付物**：actuator 适配、单关节与接触测试、官方 / Isaac 响应曲线、差异说明。

**通过条件**：关键响应达到第 02 步确定的比较标准；存在的差异能定位到参数、时序或物理实现。

**具体例子**：给同一关节相同阶跃命令，比较开始运动的延迟、上升过程和最终位置；不能只看两只小鸭都站住了。

### 第 05 步：对齐任务，用官方策略做交叉评估

**依赖**：第 04 步。

工作内容：

- 实现与目标官方运行时一致的 actor 观测、关节映射、命令编码及动作后处理。
- 对齐物理步长、50 Hz 策略更新、上一帧动作和 reset 后的初值。
- 迁移平地任务的奖励、终止条件、命令采样和随机化；actor 不读取真机无法获取的世界真值。
- 使用固定状态样本核对观测构建与策略输出。
- 将同一个官方策略放到两套环境运行相同评测序列，逐步增加命令和初始状态的覆盖。

**交付物**：Isaac 平地任务、观测 / 动作契约测试、官方策略交叉评估报告。

**通过条件**：观测与动作契约一致；两套环境的任务表现处于约定范围。差异过大时回到第 03–04 步或修正本步接口，而不是直接扩大训练量。

### 第 06 步：训练第一版 Isaac 行走策略

**依赖**：第 05 步。

工作内容：

- 先用小规模环境做短训练，检查奖励、状态数值、reset、checkpoint 和恢复。
- 再按显存和吞吐扩大并行环境数，运行平地速度跟踪训练。
- 固定评测场景和 checkpoint 选择规则，避免只挑展示效果最好的一次。
- 使用至少三个随机种子进行初步对照，记录失败样本与样本数量。
- 分开比较仿真吞吐和策略学习效果，避免将“每秒步数提高”直接称为“更快学会行走”。

**交付物**：Isaac checkpoint、训练配置、学习曲线、评测记录、失败回放。

**通过条件**：在预先确定的测试命令中满足运动指标，支持保存 / 恢复和重复评测。

**阶段成果**：到这里，Isaac 训练环境具备了实质性的可训练能力。

### 第 07 步：导出官方格式，并完成官方回放

**依赖**：第 06 步。

工作内容：

- 导出包含正确归一化的 ONNX，核对名称、形状、关节顺序、动作语义和元数据。
- 使用同一批观测比较训练端与 ONNX 推理结果。
- 按固定官方版本生成 manifest；训练配置、版本、校验值和评测结果作为旁侧文件保存。
- 在官方 CPU MuJoCo 路径加载本项目策略，运行既定测试序列。
- 记录兼容检查结果和回放失败原因。

**交付物**：完整策略包、数值一致性结果、官方回放视频与指标。

**通过条件**：导出包可被目标官方路径接受，输出数值一致，回放任务满足标准。此时标记 `sim_validated`。

**阶段成果**：第一个可以对外展示的技术 demo——在 Isaac 训练，用官方链路回放。

### 第 08 步：验证真机部署与运动表现

**依赖**：第 07 步；实际 Microduck 及其运行时访问能力。

工作内容：

- 保存当前已知可用策略及配置，建立明确的恢复路径。
- 在目标板载推理环境检查加载、输出格式、推理耗时和控制周期。
- 按官方调试与部署流程进行分阶段运动试验，检查站立、低速前进、转向和停止。
- 逐项扩大评测覆盖，记录电池状态、硬件版本、运行时、地面条件与失败结果。
- 发现系统性差异时，回到执行器、随机化或观测适配层修正，并重走导出回放。

**交付物**：真机部署说明、运行日志、运动评测与恢复操作。

**通过条件**：目标硬件上完成既定运动评测；满足标准的具体策略版本标记 `hardware_validated`。

**设备未就绪时**：本步骤保持待完成，允许继续后续仿真侧开发。任何 stub 或仿真运行都不替代硬件结果。

### 第 09 步：把动作封装成仿真与真机通用的工具

**依赖**：第 07 步；真机验证依赖第 08 步。

工作内容：

- 定义并实现最小 `RobotBackend`、工具结果、任务状态和能力发现 schema。
- 先支持 `get_capabilities`、`get_robot_state`、`run_skill`、`get_task_status`、`cancel_task` 和 `stop_motion`。
- 第一批技能基于已验证的行走能力：站立保持、受限速度行走、转向和停止；坐下等新姿态技能在验证之后再注册。
- Isaac 后端和真机后端映射相同参数、单位、状态和停止语义。
- 检查重复请求、取消确认、迟到结果、命令过期和连接中断。
- 从这一阶段就记录最小 episode 事件：请求、任务状态、动作、时间、后端、版本和结果证据。

**交付物**：双后端适配、基础技能目录、同一套工具演示脚本、事件记录器。

**通过条件**：仅切换后端配置，工具调用代码无需修改；任务成功、失败和取消有实际状态依据。

**具体例子**：相同的“以受限速度前进一段时间，然后停止”脚本分别运行于 Isaac 和真机；停止请求返回后继续跟踪到实际停止状态。

### 第 10 步：接入通用 Harness，先完成文本控制

**依赖**：第 09 步；外部 Harness 协议或用于连接验证的 stub。

工作内容：

- 实现 bridge，把外部工具调用和事件映射到已定义的工具契约。
- 向 Harness 注册实际可用技能，提交用户文本，回传进度和结果。
- 验证一个任务执行中可以查询状态，也能接受新的停止指令。
- 使用真实 Harness 时验证工具选择、结果理解和取消；外部项目未完成时，stub 只做预设映射与协议检查。
- 保持规划、长期记忆与通用调度在外部项目中。

**交付物**：bridge、文本参考应用、工具注册与事件示例。

**通过条件**：用户输入“向前走”“你现在在做什么”“停下”，能观察到对应工具调用、实际结果与正确回复。使用 stub 的结果必须明确标注。

**阶段成果**：具备语音接入前的完整控制链路，后续 ASR 只需提供文本。

### 第 11 步：加入显式录音和语音转文字

**依赖**：第 10 步的文本链路；第 01 步确认的推理资源。

工作内容：

- 基于设计中的 ASR 候选模型，在目标主机验证录音格式、中文指令效果、推理延迟和显存。
- 实现开始录音、结束提交、转写结果显示和失败重试。
- 将转写结果作为普通用户文本送给 bridge，保留录音与请求关联。
- 先用电脑麦克风调通；机载采集在第 13 步接入。
- 处理空录音、未识别到文本与转写失败；失败不自动发送动作指令。

**交付物**：ASR 服务、录音入口、转写与控制示例、语音基线指标。

**通过条件**：录音提交“向前走”，沿用第 10 步的控制路径执行；无需另建语音专用 agent loop。

### 第 12 步：加入音色设置与固定声音播报

**依赖**：第 10 步的回复文本；与第 11 步使用相同主机资源清单。

工作内容：

- 验证设计文档中的 VoiceDesign → 参考音频 → Base TTS 流程，比较中文短句、长句和不同文本的声音一致性。
- 实现描述音色、生成候选、试听、确认、保存的 setup 流程。
- 保存参考音频、文本、模型版本、校验值和活动声音指针；日常 TTS 自动读取已确认声音。
- 验证重启、新会话和仿真 / 真机切换不会丢失声音配置。
- 验证新声音生成失败或用户未确认时，旧声音保持有效。
- 日常不加载声音设计模型；记录实际常驻资源与首次合成延迟。

**交付物**：setup、VoiceProfile 存储、TTS 服务、音色一致性试听样本。

**通过条件**：确认一次“明亮、略沙哑”的声音后，不同会话的普通回复一直引用该声音版本；用户主动修改并确认后才切换。

### 第 13 步：接通小鸭本身的麦克风、扬声器和中断

**依赖**：第 11–12 步；实际音频硬件。文本和电脑音频路径可在等待设备时继续使用。

工作内容：

- 按第 01 步审读结果复用或扩展板载采音 / 播放路径，解决已有音频 worker 的设备所有权。
- 将录音片段送到外部主机识别，将合成音频传回小鸭播放。
- 实现最小参考交互界面：连接状态、开始 / 结束录音、文本备用输入、setup 入口和明确的停止动作按钮。
- 开始新录音时停止当前播音；识别到明确停止命令后走 Harness 的动作取消路径。
- 将播放开始、结束、中断和实际播放进度写入 episode。
- 在安静环境和舵机运动背景下测试录音效果，并测量完整交互延迟。

**交付物**：真实音频适配、完整语音参考应用、中断与延迟评测。

**通过条件**：用户通过小鸭麦克风下达指令，小鸭执行并用固定音色反馈；播音中断与动作取消分别符合设计。

**具体例子**：小鸭正在说话时开始录音，说话停止；录下“不要走了”并提交，动作取消后小鸭报告实际停止结果。

### 第 14 步：加入 RGB、ToF 与主动感知工具

**依赖**：第 09 步的后端与工具契约；对应传感器或仿真模型。

工作内容：

- 为 RGB、8×8 ToF、IMU 和状态实现标准帧封装、时间、坐标系、有效性和校准引用。
- 建立仿真与真机的对应传感器接口；仿真噪声和延迟逐步按真实测量标定。
- 提供 `read_sensor`、`look_at` 和 `inspect`，验证头部动作与采集时刻的关系。
- 区分获取传感器数据与识别物体身份；明确由上层 VLM 还是独立感知模型提供目标记录。
- 验证不存在的传感器、过期帧、目标无效和头部资源争用。

**交付物**：传感器后端、主动观察工具、可视化调试样例与校准记录。

**通过条件**：上层可以要求“看看左边”，获得与实际观察姿态关联的新鲜数据；ToF 无效测量不会被当作前方空旷。

### 第 15 步：完成目标交互与可追溯的养成体验

**依赖**：第 10、13、14 步；整体 agent 验证需要真实外部 Harness。

工作内容：

- 先做受限场景中的静态目标接近，再做移动目标跟随；不把复杂全屋导航作为首个验收场景。
- 实现 `approach_object` / `follow_object` 所需的目标有效性、距离判断和快速反馈循环，声明目标丢失与取消行为。
- 使用已验证的行走策略执行速度命令；不要求为了展示目标交互就立刻训练完整 VLA。
- 补全 episode 的传感器、语音、工具和执行证据，提供事件回放。
- 将事实与证据引用交给 Harness 的长期记忆接口，保持 sim / real 经验标记。

## 3. 如何管理每次开发

每次工作围绕一个当前步骤中的可验收结果进行，提交说明至少包含：

| 项目 | 要记录什么 |
|---|---|
| 本次目标 | 一个具体行为，例如“官方策略在 Isaac 中完成固定转向序列” |
| 实际修改 | 相关实现、配置及资产版本 |
| 验证证据 | 命令、配置、指标、日志或回放引用 |
| 未完成项 | 差异、缺失设备或外部接口；是否阻塞下一步 |
| 下一项工作 | 紧接着要完成的单一结果 |

遇到验证失败时，先保留失败样本并定位差异，再调整实现。运动侧不通过时不把问题交给上层大脑补偿；上层任务错误也不应通过改行走 policy 来掩盖。

可在第 02 步完成后估算第 03–08 步的工期；在第 11–12 步完成主机模型验证后估算真机语音集成工期。当前没有 GPU 型号、现成权重和真机可用性信息，不将训练等待时间写成固定日历承诺。
